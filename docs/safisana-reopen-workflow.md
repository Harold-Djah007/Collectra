# Safisana drying-bed reopening

The editable Processing - Plant app can gain an offline request form through `stage_safisana_reopen_requests`. A worker chooses the bed, optionally gives the batch date or name, and explains the mistake. The form changes no case. Once submitted and synced, a Safisana HQ user with data editing, reporting, project, and all-location access can review the submission in the dashboard and find the original closed case in Case List.

No Azure database access is needed for reopening. After reading the worker's request, an authorized HQ supervisor selects **Review and reopen case** on that request, enters the original closed case ID from Case List, and uses **Check case**. HQ shows links to the matching case and its closing submission. After inspecting both, the supervisor acknowledges that archiving removes the whole closing form from active reports and selects **Archive closing form and reopen this case**. The server checks the case and closing form again before applying HQ's existing archive action. The original case ID reopens; a duplicate case a worker created afterward remains separate. Have the worker sync before looking for the original case again. The dashboard shows recent requests, not approval status, and a request continues to appear there until it ages out of the 30-day window.

Archive the **closing form**, never the case itself. Archiving that form also removes all its other answers from active form reports and exports. If it contains drying-bed monitoring readings, stop and review how those readings must be retained or re-entered before archiving. Do not archive a registration form that created the case or another form selected by name alone.

Run the staging command without `--apply` to inspect the XML first. `--apply` adds the form only to the editable app; it does not release a mobile build or alter submitted cases. Repeating it fails rather than creating a second request form.

Optional local inspection: `inspect_safisana_reopen_case CASE_ID --output-dir PRIVATE_DIRECTORY` writes the closing submission and a review-only copy with its close action removed. Its XML outputs can contain submitted data; keep them private. It does not edit the form or reopen the case, and it needs only the Collectra HQ environment, not access to Azure.

The button uses the established HQ archive operation and checks that the chosen form closes exactly one case and does not also create a case. It refuses an ambiguous closing history or a case that is no longer closed. It deliberately does not promise to keep readings on an archived closing form in active exports. Cases with ambiguous names require the supervisor to verify the original case ID before approval.

## Pilot a separate close action

Run `stage_safisana_close_only --output-dir PRIVATE_DIRECTORY` to review the proposed monitoring XML and separate closing form. This preview changes no app, case, calculation, case ID, or Azure data. The existing `/data/close_batch` values and final-measurement questions remain in the monitoring form, but its future case-close action moves to a new form that requires an existing drying-bed case. The question label explains that the worker must save measurements first, then submit **Close drying-bed batch**. Closing only collects a yes confirmation and reason; it records no measurement. This lets HQ later archive the dedicated close form while retaining the earlier measurement submission.

First run `test_reopen_archive_integration.py` and `test_stage_safisana_close_only.py` in WSL's Django **test database**. The integration test creates synthetic cases, archives both a close-only submission and a combined monitoring/closing submission, and checks the different outcomes. A passing test does not replace a mobile sync pilot or review of downstream reports that use `/data/close_batch` as a signal. Do not use real migrated cases to test the button.

After reviewing the XML, the optional `--apply` flag writes a backup and changes only the editable app draft; it does not publish a build or alter old submitted forms. Publishing a new build requires an explicit app review. Mobile devices still running an older build can continue to submit the old combined monitoring/closing form until they update. Validate both the old and new build paths during rollout, and check any downstream Azure process that interprets `close_batch = yes`.
